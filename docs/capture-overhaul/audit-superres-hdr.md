# Audit: pixel-shift super-resolution and LED-exposure stack (openflexito webapp)

All paths under `webapp/src/lib/` unless noted. Nothing was edited. Two numerical checks were run with the repo's own `displacement` and `grayDown` code on a synthetic non-periodic scene (scripts `regtest.ts`/`regtest2.ts` in this directory); results are marked **measured**. Everything else is read from the source. Hypotheses are labelled.

## 1. Super-resolution: current behaviour (facts)

- **Shots and pattern**: `frames` option → `side = round(sqrt(max(4, frames)))`, default 9 = 3×3 raster (`services/photoService.ts:315-316`, `:344-347`). Between shots the stage moves `stepX`/`stepY` motor steps as raw moves (`compensate: false`). A return move undoes the raster at the end (`:355`).
- **Commanded offset → pixels**: `pxPerStepX = |calX.pixelsPerStep| × (fullWidth / csm.imageWidth)` (`:321-323`; `csm.imageWidth` is the frame size the calibration was measured at, `store/calibration.svelte.ts:8`). `stepX = max(1, round(0.5 / pxPerStepX))` (`:325`): the target is ~0.5 full-resolution px per hop. Only the magnitude of each axis's pixel vector is used; the 2×2 rotation matrix (`algo/csm.ts:142`) is not consulted, so rotation between stage axes and sensor is absorbed by measuring the shift, not by planning it.
- **Consequence of 0.5 px × 3×3**: the sub-pixel phases along each axis are {0, 0.5, 1.0}: the third column/row has the same phase as the first. A 3×3 grid at 0.5 px yields only 2×2 distinct phases (4 useful frames of 9). A 3×3 pattern would need 1/3 px hops, which is what the drizzle unit test itself uses (`algo/__tests__/drizzle.test.ts:12`). The raster also resets x by −(side−1)·stepX at each row start, a direction reversal of 1-2 motor steps that the stage backlash (fitted in hundreds of steps, `csm.ts:102`) will swallow. Hypothesis: on hardware several frames land at near-identical positions.
- **Shift measurement**: `workers/superresWorker.ts:26-32`. Each still is reduced by `grayDown` (`algo/stack.ts:96`, integer box downscale to ≤410 px wide: factor **8** for 3280 px, 4 for the 1640 mode), then `displacement()` (`algo/fftTrack.ts:36`) runs on the whole downscaled frame: zero-mean, zero-pad to 2× (1024×1024 FFT), high-pass 1−Gaussian σ 10 px, cross-power, integer peak, then the average of a 1-D parabolic fit and a background-subtracted centroid of the >90 % region in an 11×11 window (`:53-71`). The result is multiplied back by the downscale factor. `quality` (peak / highest value outside an 8 px ring) is recorded but never used to reject a frame (`superresWorker.ts:34-35`).
- **Combination**: `algo/drizzle.ts:24`: output scale **2**, `pixfrac` **0.8** (the default; the unit test that demonstrates the gain uses 0.3, `drizzle.test.ts:63`), square drop, area-overlap weights, output = weight-normalised mean of RGB per output cell; uncovered cells filled by ≤8 dilation passes (`:71`). Output is 8-bit RGBA saved as PNG (`photoService.ts:362`). No deconvolution or sharpening after drizzle.
- **Colour / input data**: inputs are the decoded **JPEG** RGBA from `/snapshot.jpg?full=1` (`:319`, `:350`), already demosaiced, gamma-encoded, ISP-sharpened and JPEG-compressed. The Bayer mosaic is not used, although `fetchRaw` (`:81`) and the RAW worker already exist for other modes.
- **Crop**: frames wider than 4096 px on the long side are centre-cropped before registration (`:71-78`, `:320`, `:350`). With the IMX219 (3280 px) it never triggers; `crop` is `null` in practice. The 2× output is 6560×4928 (~130 MB RGBA), which is the actual memory risk.
- **Timing**: after each move `settle(150)` + `waitForFrames(2, 1500)` (`:348`), then the still, which is itself a ~1.3 s mode switch. Exposure and AWB are frozen per still from the latest live frame by the device (`device/openflexito/camera.py:436-449`). `waitForFrames` resolves silently on timeout (`api/sampler.ts:9-16`).
- **Optics**: README records 88 ± 6 nm/step in xy and 50 nm/step in z (`README.md:230`) but no objective magnification or µm/px. The ~0.35 µm/px figure in the brief could not be verified from the repo. If it holds: Abbe limit for NA 0.65 at 550 nm ≈ 0.52 µm, Nyquist requires ≤0.26 µm/px, so luminance is ~1.35× undersampled and each Bayer colour plane (0.7 µm pitch) ~2.7× undersampled. A 2× drizzle can recover at most ~1.3× in luminance resolution but substantial colour resolution, and only if it works on the mosaic rather than on demosaiced JPEGs. With 88 nm/step and 0.35 µm/px, one motor step ≈ 0.25 px, so `stepX` = 2 steps.

## 2. LED-exposure ("HDR") stack: current behaviour (facts)

- **Levels**: factors `[0.4, 0.7, 1, 1.5]` × current `light.cc`, each clamped to [0.02, 1], rounded to 3 decimals and deduplicated (`photoService.ts:182-185`). At full brightness only three levels remain; fewer than two throws.
- **LED control**: `device.setLight(cc)` (`store/device.svelte.ts:123`) → RPC `light.set {cc}` (`device/openflexito/app.py:167-175`) → `led_cc` on the Sangaboard (`sangaboard.py:191`). README states this is a DC constant current set through the TPS61060 step interface, not PWM; only the auxiliary PWM outputs are chopped. `device/openflexito/leds.py` is the Pi's status LED and is unrelated to illumination.
- **Camera lock**: if AE is enabled and the latest frame reports exposure and gain, `AeEnable:false` with those values is set for the run and AE is re-enabled afterwards (`photoService.ts:189-191`, `:201`). AWB is **not** locked in the browser; the device's still path freezes whatever colour gains the latest live frame had at that moment (`camera.py:447-448`), so each level can carry a different white balance.
- **Timing**: `settle(250)` + `waitForFrames(3, 2000)` after each LED change (`:196`), then the still.
- **Merge**: `exposureFuse` (`algo/stack.ts:131`): per 8×8 block, weight = exp(−(mean luminance − 0.5)² / (2·0.2²)) + 1e-4 (well-exposedness only), normalised, 3 box-blur passes, normalised again, then a per-pixel bilinear blend of the gamma-encoded JPEG values between cell centres (`:67-93`). This is single-scale Mertens-style exposure fusion, without the contrast and saturation terms and without a pyramid. There is no camera-response recovery, no linearisation, no tone mapping; output is an 8-bit JPEG at quality 0.95 (`:204`, `:48-52`). The result is display-referred, not radiance.
- **Linearisation**: JPEG values are not linearised before blending. For Mertens fusion, which is defined on display-referred images, that is acceptable; it is only a defect if the mode is meant to produce radiance (HDR), which it currently is not.
- **Tests**: `__tests__/stack.test.ts:45-55` checks that a checker survives a dark/bright pair. No test covers colour consistency, more than two frames, or halos.

## 3. Defects and risks (with evidence)

1. **Sub-pixel registration at the worker's downscale is not accurate enough for the shifts commanded** (measured, synthetic random-blob scene, downscale 4 = the 1640 mode; the 3280 mode uses 8 and is worse):

   | true shift (full px) | measured | error |
   |---|---|---|
   | (8, 0) | (8.00, 0.00) | 0.00 |
   | (0.25, 0.15) | (0.10, 0.06) | 0.18 |
   | (0.5, 0.3) | (0.20, 0.12) | 0.36 |
   | (0.5, 0.5) | (0.20, 0.20) | 0.43 |
   | (1, 1) | (0.41, 0.41) | 0.84 |
   | (1.5, 0.9) | (−8.19, 43.96) | 44.1 |
   | (2, 1.2) | (−8.00, 44.07) | 44.0 |
   | (4, 4) | (4.00, 4.00) | 0.01 |

   Integer shifts at the registration scale are exact; sub-pixel shifts are underestimated by ~2.5× and some intermediate shifts fail outright. The same `displacement()` on a 410×308 central crop at **full resolution** gave errors of 0.03-0.07 px on every case tested (0.25 to 3 px). Registration error of the order of the commanded shift defeats drizzle: frames are splatted at wrong phases and the output is a blurred average rather than a super-resolved image. Hypothesis for the mechanism: the centroid over the thresholded 11×11 window is biased toward the integer sample, and averaging it with the parabolic estimate halves the offset; the 44 px outliers come from a secondary lobe on the broad, high-passed correlation surface.
2. **Quality gate is uninformative and unused**: quality was 1.0-1.2 for both exact and 44 px-wrong results. Nothing rejects a mis-registered or duplicate frame (`superresWorker.ts:34-35`); the values are only stored in the gallery item.
3. **Phase diversity**: 3×3 at 0.5 px duplicates phases and the row-start reversals are within backlash (see §1). Hypothesis pending a hardware check of the recorded `shifts`.
4. **pixfrac 0.8 at scale 2** means each drop spans 1.6 output cells, box-blurring the reconstruction over 0.8 input px on top of the sensor pixel aperture. The unit test shows the benefit with 0.3.
5. **Drizzling gamma-encoded, ISP-sharpened, JPEG-compressed frames**: averaging in gamma space biases edge positions; ISP sharpening halos and 8×8 JPEG block artefacts are treated as scene content by both registration and drizzle. Colour resolution already lost in the ISP demosaic cannot be recovered.
6. **No AWB lock during the LED stack** (`photoService.ts:190-191` vs `camera.py:447-448`): white-LED chromaticity changes with drive current and each still freezes the live AWB of that instant, so levels can differ in tint and the block blend produces local colour shifts. Grounded in the code path; not observed on hardware.
7. **Exposure fusion is not HDR**: no linear data, no radiance merge, no 16-bit output, unlike the `focusfineraw` path. The mode name "HDR counterpart" in README oversells it.
8. **Single-scale block fusion** with only a well-exposedness term: halos are expected where neighbouring 8 px blocks choose different frames, even after 3 smoothing passes. Not measured.
9. **Test coverage**: the only registration test tolerates 0.75 px error at the tracker's own scale (`__tests__/autofocus_track.test.ts:96-98`); there is no sub-pixel test for `displacement`, no `superresWorker` test, and the drizzle test feeds known offsets. The registration weakness is invisible to the suite.
10. Minor: `centerCropRgba` at 4096 never triggers for IMX219; the ×2 PNG encode of 6560×4928 is the real memory risk. `settle(150)` after a 1-2 step move is probably ample, but flexure creep after a reversal is unmeasured.

## 4. Improvement ideas (ranked)

| # | Idea | Gain | Cost | Risk |
|---|------|------|------|------|
| 1 | Register at full resolution on a central crop (e.g. 512×384), or coarse-to-fine: downscaled integer estimate then full-res refinement (what `algo/align.ts` `SliceAligner` already does for focus stacks). Reject frames whose refined shift is > ~0.15 px from a valid phase or duplicates another frame. | Measured 0.36-0.84 px error → ~0.05 px; prerequisite for any real gain. | Low: reuse `SliceAligner`; one worker change. | Low. |
| 2 | Fix the pattern: 2×2 at 0.5 px for scale 2 (or 3×3 at 1/3 px for scale 3), planned in the CSM-rotated frame, all hops in one direction per axis (backlash pre-loaded, snake order); optionally extra randomised frames. Check phase diversity from measured shifts before drizzling. | Every frame contributes a distinct phase; halves capture time or doubles useful data. | Low. | Stage repeatability at 1-2 steps unknown; log `shifts` on hardware. |
| 3 | Lower pixfrac to 0.4-0.5 once registration is accurate; expose scale/pixfrac as advanced settings. | Sharper output; effect already shown by the unit test. | Trivial. | More holes with few frames (fillHoles handles). |
| 4 | Drizzle the raw Bayer mosaic (`/raw.bin`, via existing `fetchRaw`) per CFA plane onto a common 2× grid, then apply the existing `rawdev` pipeline (black level, LSC, WB, CCM, gamma) skipping demosaic. Classic 4-shot 1-px pattern gives full RGB per site. | True colour super-resolution; no ISP sharpening/JPEG artefacts; linear-light averaging; 16-bit output via `png16.ts`. | Medium-high: 16 MB × N transfers (~15 s each), new worker path, per-plane registration. | Browser memory; 9 frames ≈ 3 minutes. |
| 5 | Post-drizzle Wiener or Richardson-Lucy deconvolution with PSF = drizzle kernel ⊗ pixel aperture ⊗ measured optical blur (bead or edge). | Recovers MTF loss of aperture and drop; visibly sharper. | Medium: pure algo module plus a PSF-measurement UI. | Noise amplification and ringing if PSF is wrong; needs regularisation and tests. |
| 6 | Exposure stack: camera-exposure bracketing (ExposureTime ×0.5/1/2 via `camera.set_controls`) in addition to or instead of LED levels; lock `AwbEnable` and `ColourGains` for the run. | Removes LED chromaticity drift; exact exposure ratios enable radiance merge. | Low. | Exposure-time changes alter frame duration on IMX219; needs settle. |
| 7 | True HDR from RAW: linear 10-bit frames merged as radiance (Debevec weights, known exposure ratios), then Mertens or Reinhard tone map; 16-bit PNG + preview. | Real dynamic-range extension rather than a blend; consistent with `focusfineraw`. | Medium: N raw downloads; new `algo/hdr.ts`. | Slow capture; LED-ratio path needs a measured cc→flux curve. |
| 8 | Multi-scale Mertens for the JPEG path (reuse the Laplacian pyramid in `pyramidFuse.ts`) with contrast and saturation terms. | Removes block halos; standard quality. | Low-medium. | None significant. |
| 9 | Flat-field per LED level (dark + bright references) applied before either merge. | Removes vignetting that biases block weights and drizzle brightness. | Medium. | Needs per-session calibration images. |
| 10 | Tests: sub-pixel `displacement` test at 0.1-0.5 px with 0.05 px tolerance at full and downscaled sizes; worker-level end-to-end test with shifted synthetic frames; AWB-lock assertion for the LED stack. | Makes defects 1, 2 and 6 visible to CI. | Low. | None. |

Recommended order: 1, 2, 3, 10 first (a day of pure-TS work with existing tests as templates), then 6 for the LED stack, then 4 and 7 as the RAW-based follow-up.
